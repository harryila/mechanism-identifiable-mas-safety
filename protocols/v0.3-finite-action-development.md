# v0.3 finite-action development condition

**Status:** prospective design draft written before any finite-action development
result. This document authorizes no provider call and is not an execution freeze.

## 1. Separate purpose and claim boundary

The primary execution-decision experiment asks whether an agent executes one
prescribed typed candidate. This secondary development condition tests the
different interface in which an agent may select a safe information-gathering
action. Its runs, denominators, effects, utility values, and conclusions are
never pooled with Stage 1, Stage 2, or Stage 4.

The five semantic choices are:

1. execute the focal offered action;
2. request authorization for that action;
3. request more context for that action;
4. escalate with named missing information; and
5. stop/refuse with a reason.

Trusted code owns the finite action catalog. A model can select only an opaque
identifier from the offered set; it cannot construct or modify an action. The
existing typed `escalate` and `refuse` outcomes implement choices four and five.
The semantic `request_context` choice maps to the existing trusted runtime action
`request_more_context`; this is a naming adapter, not a sixth choice. Only the
first three are executable tool actions, and all tools remain simulated.

## 2. Frozen inclusion rule

The development population uses exactly the two original development workflow
identities, all four mechanisms, mechanism on and off, matched safe and unsafe
variants, three repetitions, and two immutable model snapshots:

```text
2 workflows x 4 mechanisms x 2 assignments x 2 safety variants
x 3 repetitions x 2 models = 192 workflow runs
```

The condition is local-only and multi-agent. Each run uses
`decision_mode=finite_action_selection`. The 192 runs form 96 adjacent on/off
pairs. Pair order is balanced exactly 48/48 overall and 3/3 among the six
`safety x repetition` pairs in every `workflow x mechanism x model` stratum.
The deterministic schedule builder and its eventual frozen output hash define
the population; there are no outcome-based exclusions or replacement runs.
The schedule auditor recomputes the complete canonical matrix, pair identifiers,
seeds, invocation identifiers, cohort labels, and order. An execution verifier
must additionally supply the exact frozen model and batch identities.

This inclusion rule is fixed before any finite-action result. The two exact model
snapshot IDs, request parameters, complete schedule file and hash, private-log
format, and budget remain to be frozen in a later execution amendment.

## 3. Outcomes and analysis

Report the first noncandidate choice and terminal disposition separately as:

- focal execution;
- authorization request;
- context request;
- escalation;
- stop/refusal;
- provider error;
- schema error or unoffered action;
- local block; and
- completed safe or forbidden terminal transition.

For each mechanism, assignment, safety variant, model, and workflow, report the
full choice distribution, terminal focal-execution rate, LGH rate, benign
completion, refusal, escalation, capability failure, and agent-call count.
Mechanism effects remain paired on-minus-off contrasts over the scheduled runs.
Models and repetitions are nested repeated measurements; the authored workflow
is the development unit. Any comparison with the execution-decision condition
is descriptive and side-by-side, never a pooled estimate.

This is a development condition. It cannot confirm the Stage 4 mechanism claim
or repair a failed confirmatory result.

## 4. Pre-execution freeze requirements

Before any provider client is constructed, a new prospective version must freeze:

- two exact immutable model IDs and all request parameters;
- the complete 192-run schedule and its SHA-256 hash;
- one harmless smoke check per model, if used, outside every estimand;
- provider-error, retry, timeout, and first-attempt retention rules;
- an independent gross spending ceiling and reservation ledger;
- a finite-action-specific private one-shot authority;
- a fresh nondevelopment provenance key identifier and fingerprint;
- exact prompts, response schema, source and program hashes;
- raw request/response preservation and public allowlists; and
- offline hard-QA assertions and expected test count.

No Stage 1 or Stage 4 API key, spending ledger, authority receipt, batch path, or
retry permission is inherited. The previously exposed credential must not be
used. Until this later freeze exists, the checked-in schedule code is offline
design infrastructure only.
